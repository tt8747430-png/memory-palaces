# ADR 0005 — Sync: a cycle the learner can see, merged against what each device saw

- **Status:** accepted · **Date:** 2026-09 · consolidated 2026-10

The cycle is `features/sync/sync-now.ts` and `quiet-sync.ts`; replication and Realtime are `SyncManager` and
`cloud-watcher.ts` (`shared/api/supabase`); scheduling is `SyncProvider`, `use-autosync.ts`, `use-quiet-sync.ts` and
`use-first-sync.ts` (`app/providers`); the server side is `push_documents` in `supabase/migrations`; merging is
`mergeFields` (`shared/lib/merge-fields.ts`), `mergeAgainstBase` (`shared/api/rxdb/conflict-handlers.ts`) and the
entity handlers in `app/persistence/conflict-handlers.ts`. What may wait on the network is
[ADR 0004](0004-what-needs-the-network.md).

## Context

- Replication ran live. The learner was never told what was pending, never asked before a deletion made offline
  went out, and had no way to say "not yet".
- The server compared document clocks, and the handlers kept the newer whole document. A phone that studied a card
  saved the whole card with a new clock, pushed, and wrote the old back over a typo fixed on the tablet. No conflict
  was raised and both banners said everything was synchronised. The same shape lost XP (two devices earning on 100
  settled at `max`), deck renames, folder moves and profile edits. A newer clock says "this write is later", not
  "this write saw yours".
- Once every write was logged, a theme change or an opened Library row read as "changes waiting" beside the cards.

## Decision

**A Sync is one cycle the device runs when asked.** Nothing leaves the device until the learner presses
Synchronise or Autosync (a preference, on by default) asks for them. `syncNow` peeks the ids changed in the cloud
since this device's own checkpoint, classifies them against the pending-change log, runs one `live: false` cycle
and confirms. A failed Sync at any phase leaves the log and the checkpoints untouched. One cycle runs at a time; a
request the running cycle covers joins it, any other chains behind it.

- **Every synced write waits in the pending-change log** until a Sync confirms it: each store gets a
  `PendingChangePort` (extensions through `context.pending(key)`). One entry per document holds its net state since
  the last Sync. Confirming clears entries by `at`, so a write made during the cycle stays pending. The checkpoint
  then steps forward only through rows this cycle pushed (`stepOverOwnEcho`) and stops at anyone else's, so it can
  only lag, which over-reports and never under-reports.
- **Two cadences.** _Held_ tables wait to be asked: decks, cards, folders, questions, progress, history, and every
  extension table unless it declares otherwise. _Quiet_ tables, preferences and profiles, go by themselves whenever
  there is an account and a connection (`quietSync`): no question, no Sync log line, no move of `lastSyncedAt`, never
  counted as waiting, never raising the banner. Autosync governs held tables only.
- **Autosync** runs a held Sync on reconnect, on `visibilitychange`, on `pagehide`, 4 s after writes settle, and 3 s
  after the cloud is reported changed. A failed run retries after 15 s, 60 s, then 5 min while online and visible.
  With Autosync off nothing runs by itself.
- **Only a destructive divergence asks.** Everything else merges. The questions are: a document deleted here and
  changed elsewhere, and a deck or folder deleted here that another device added to, edited inside or moved a deck
  into (found from parent ids alone, to any depth, and reported on the container). A deletion pushed to a cloud that
  has not moved is never a question, however large. `SyncReviewDialog` defaults each row to **Delete**, with **Keep**
  as the override; dismissing it cancels the whole Sync. Delete re-deletes now with a fresh clock and tombstones the
  unseen descendants; Keep restores the cloud copy and the subtree the deletion took (`keepCloudCopy`).
- **An account's first Sync on a device holds the splash** when it has never completed one here and Autosync is on.
  Every outcome releases it, and so does `FIRST_SYNC_BUDGET_MS` (10 s), after which the cycle carries on under the
  banner. **Open now** lets the learner in sooner. If the pulled preferences switch an extension on, a second cycle
  brings its rows in first. It never covers a question.
- **Realtime only lights the banner.** One watcher per signed-in account, filtered by `user_id`, reports positions;
  a position past this device's checkpoint sets `cloudChanged`. A re-subscription counts as a possible change.
- **A push says which server copy it was based on, the server refuses a write over any other, and a conflict is
  merged field by field against that copy.**
  1. RxDB records the server copy each device last saw (`assumedMasterState`). Its `updatedAt` travels with the row as
     `base` (`null` if never pulled), and `base_deleted` says whether it was a deletion.
  2. `push_documents` applies a based row when it holds no copy, holds exactly this data, or holds the copy the row
     names; anything else comes back. Each document is held by a transaction-scoped advisory lock, taken in id order,
     so the check and the write see the same copy.
  3. `mergeFields` keeps a field only one side changed and settles a field both changed by a rule (`srs` merged, XP
     and streak freezes summed as deltas from the base, a preference to the device making the write) or by the newer
     clock; it carries a deletion and stamps the later clock. RxDB pushes the result again on top of the copy it was
     refused over. With no base, the newer whole document wins, counters take the `max`, and preferences count what
     differs from the defaults as this device's change. History entries are never edited, so history is
     first-write-wins.
- **Nothing hangs.** Every PostgREST call a Sync makes carries a 30 s timeout, and id lookups go 100 at a time.

## Consequences

- A device lost before it syncs loses what it had not synced. Accepted; the banner and Autosync are the mitigation.
- No conflict handler may assume two versions: each is `mergeAgainstBase({ against, without })` or built from it, and
  an extension's collection gets the generic one. A counter that must add up needs a `both` rule. A new table needs
  only its place in `push_documents`' allow-list.
- **Nothing may drop what a device saw.** `replicationState.remove()` deletes every `assumedMasterState` with the
  checkpoint and turns each waiting change into a base-less push. Repair (`SyncManager.rereadEverything`) passes over
  the checkpoint only.
- A row without `base` keeps the clock rule. That branch serves builds shipped before 2026-09-18 and goes with a later
  migration.
- A remote edit landing between the peek and the cycle is applied unasked. It stays ahead of the checkpoint, so the
  next Sync reports it.
- Signing into another account with unsynced work asks first ([ADR 0004](0004-what-needs-the-network.md)).
